# Выбор и настройка мониторинга в системе

## Мотивация

### Почему в систему нужно добавить мониторинг

Компания «Александрит» находится в критической ситуации:
- Клиенты жалуются на потерянные и задержанные заказы
- Компания уже потеряла несколько крупных контрактов
- Операторы жалуются на медленную загрузку MES-дашборда
- Команда не понимает причин проблем ("как слепые котята" — сделали пагинацию и фильтры, но это не помогло)

**Текущее состояние:** система работает "вслепую". Нет объективных данных о производительности, нагрузке и узких местах. Решения принимаются на основе догадок, а не фактов.

**Ключевая проблема:** без мониторинга невозможно:
1. Понять, где именно "теряются" заказы
2. Определить причину медленной работы MES
3. Оценить влияние API-канала на основной бизнес (B2C)
4. Предсказать проблемы до того, как они повлияют на клиентов, или хотя бы отреагировать на проблему быстро, не дожидаясь массовых жалоб
5. Оценить эффективность оптимизаций

### Что мониторинг даст компании

| Проблема | Что даст мониторинг |
|----------|---------------------|
| Потеря заказов | Отслеживание DLQ в RabbitMQ, выявление "застрявших" сообщений |
| Медленный MES | Метрики latency, CPU, Memory — понимание узких мест |
| Влияние API на B2C | RPS по сервисам и пользователям, сравнение нагрузки |
| Рост нагрузки | Прогнозирование capacity по CPU, Memory, connections |
| Проблемы с очередями | Messages in flight, DLQ — состояние очередей |

**Бизнес-эффект:**
- Сокращение времени обнаружения проблем (MTTD)
- Сокращение времени восстановления (MTTR)
- Проактивное решение проблем до жалоб клиентов
- Раннее оповещение о проблемах именно тех людей, которые могут эту проблему решить
- Обоснованные решения по оптимизации и масштабированию
- Возможность установить и отслеживать SLA/SLO

## Выбор подхода к мониторингу

Для разных частей системы оптимальны разные подходы:

### RED (Rate, Errors, Duration) — для API-сервисов

**Применяется к:** Shop API, CRM API, MES API

RED-метод разработан специально для сервис-ориентированных архитектур и отвечает на вопрос: "Как чувствуют себя мои пользователи?"

- **Rate** — количество запросов в секунду 
- **Errors** — количество неуспешных запросов (в первую очередь HTTP 500)
- **Duration** — время обработки запросов 

**Почему RED для API:**
- Все три сервиса — это HTTP API, обслуживающие пользователей
- RED даёт полную картину пользовательского опыта
- Предоставленный список метрик хорошо ложится на RED-подход

### USE (Utilization, Saturation, Errors) — для инфраструктуры

**Применяется к:** PostgreSQL (Shop DB, MES DB), RabbitMQ, S3, серверы приложений

USE-метод оптимален для ресурсов и отвечает на вопрос: "Хватает ли ресурсов?"

- **Utilization** — процент использования ресурса (CPU %, Memory %)
- **Saturation** — степень "переполнения" (connections, messages in flight)
- **Errors** — количество ошибок (DLQ)

**Почему USE для инфраструктуры:**
- Базы данных, очереди, хранилища — это ресурсы с ограниченной ёмкостью
- USE позволяет предсказать проблемы до их возникновения
- Критично для планирования масштабирования

## Метрики из предложенного списка

### Группа 1: RabbitMQ

---

#### ✅ Number of dead-letter-exchange letters in RabbitMQ

**Выбрана: ДА**

**Зачем нужна:**  
Это критически важная метрика для компании. DLQ (Dead Letter Queue) содержит сообщения, которые не удалось обработать — потенциально это и есть "потерянные" заказы, на которые жалуются клиенты. Ненулевое значение DLQ требует немедленного внимания.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `queue` | `<имя_очереди>` | Понять, в какой очереди происходят сбои |
| `reason` | `rejected`, `expired`, `max_retries` | Понять причину попадания в DLQ |

---

#### ✅ Number of messages in flight in RabbitMQ

**Выбрана: ДА**

**Зачем нужна:**  
Messages in flight — это сообщения, которые были отправлены консьюмеру, но ещё не подтверждены (unacked). Высокое значение указывает на проблемы с обработкой: консьюмер не справляется или завис. Это индикатор saturation очереди.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `queue` | `<имя_очереди>` | Определить, какая очередь перегружена |
| `consumer` | `crm-api`, `mes-api` | Понять, какой консьюмер не справляется |

---

#### ✅ Number of requests (RPS) for Shop API

**Выбрана: ДА**

**Зачем нужна:**  
Базовая метрика нагрузки на онлайн-магазин. Позволяет отслеживать рост трафика (100 заказов/месяц), выявлять пики нагрузки, планировать масштабирование. Необходима для расчёта error rate.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|

| `method` | `GET`, `POST`, `PUT`, `DELETE` | Разделить чтение и запись |

---

#### ✅ Number of requests (RPS) for CRM API

**Выбрана: ДА**

**Зачем нужна:**  
Нагрузка на CRM от продавцов. Важно для понимания рабочих паттернов (пики в рабочее время), планирования capacity.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `endpoint` | `<имя_эндпоинта>` | Распределение по функциям |
| `method` | `GET`, `POST`, `PUT` | Тип операции |

---

#### ✅ Number of requests (RPS) for MES API

**Выбрана: ДА**

**Зачем нужна:**  
Критически важная метрика! MES обслуживает и операторов (внутренний трафик), и внешних API-пользователей. Именно внешний API "завалил" систему заказами. Необходимо разделять эти потоки.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `endpoint` | `<имя_эндпоинта>` | Распределение нагрузки по эндпоинтам |
| `method` | `GET`, `POST` | Тип операции |
| `source` | `internal`, `external_api` | **Критично:** разделить внутренний и внешний трафик |

---

#### ✅ Number of requests (RPS) per user for Shop API

**Выбрана: ДА**

**Зачем нужна:**  
Выявление аномального поведения пользователей (боты, парсеры, атаки). Также полезно для понимания паттернов использования и настройки rate limiting.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `user_type` | `anonymous`, `registered` | Разделить анонимных и зарегистрированных |

*Примечание: хранить метрику по каждому user_id нецелесообразно из-за высокой кардинальности. Лучше агрегировать по типам или использовать для расчёта percentiles.*

---

#### ⚠️ Number of requests (RPS) per user for CRM API

**Выбрана: ЧАСТИЧНО**

**Зачем нужна:**  
CRM используют продавцы — их количество ограничено. Метрика может быть полезна для выявления "тяжёлых" пользователей, но менее критична, чем для Shop/MES.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `role` | `seller`, `admin` | Разделить по ролям |

*Примечание: можно отложить до второй очереди внедрения.*

---

#### ✅ Number of requests (RPS) per user for MES API

**Выбрана: ДА**

**Зачем нужна:**  
Критически важно для внешнего API! После открытия API компанию "завалило" заказами от партнёров. Нужно понимать, кто из API-пользователей создаёт основную нагрузку, для настройки rate limiting и переговоров с партнёрами.

**Ярлыки:**
| Ярлык | Значения | Зачем |
|-------|----------|-------|
| `source` | `internal`, `external_api` | Разделить внутренний и внешний трафик |
| `api_client` | идентификатор клиента API | Выявить крупных потребителей |

## Показатели насыщенности (Saturation)

Насыщенность (Saturation) — это мера того, насколько ресурс близок к исчерпанию. В отличие от утилизации, которая показывает текущее использование, насыщенность показывает "очередь" — сколько работы ждёт выполнения.

### Определение пороговых значений

#### 1. CPU Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| CPU % | > 70% | > 85% | При CPU > 70% начинается рост latency. При > 85% система становится нестабильной, возможны таймауты |
| Load Average (1 min) | > число ядер × 0.7 | > число ядер × 1.0 | Load Average показывает очередь процессов. При LA > числа ядер процессы ждут CPU |

**Почему эти значения:**
- 70% — есть запас для пиков нагрузки
- 85% — минимальный запас, требуется срочное вмешательство
- При 100% CPU система деградирует, растут таймауты, пользователи страдают

#### 2. Memory Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| Memory % | > 80% | > 90% | При высокой утилизации начинается swap, резко падает производительность |
| Swap Usage | > 0 (любое использование) | > 100 MB | Swap = деградация производительности. В продакшене swap должен быть минимален |

**Почему эти значения:**
- 80% — запас для пиков и кэширования
- 90% — система на грани, OOM Killer может убить процессы
- Любой swap — уже проблема для latency-sensitive приложений

#### 3. Database Connections Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| Active connections / Max connections | > 70% | > 90% | При исчерпании пула новые запросы будут ждать или получать ошибки |
| Waiting connections | > 0 | > 10 | Наличие ждущих соединений = очередь, пользователи ждут |

**Почему эти значения:**
- 70% — нормальный запас для burst нагрузки
- 90% — критично, один всплеск может исчерпать пул
- Waiting > 0 — уже есть очередь, latency растёт

**Специфика для Shop DB:**
- Shop DB используется двумя сервисами (Shop API и CRM API)
- Рекомендуется снизить пороги до 60% Warning / 80% Critical
- Мониторить соединения с разбивкой по клиентам

#### 4. RabbitMQ Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| Queue depth (ready messages) | > 1000 | > 10000 | Большая очередь = консьюмеры не справляются, заказы ждут обработки |
| Messages in flight (unacked) | > 100 | > 500 | Много unacked = консьюмеры медленно обрабатывают или зависли |
| Message age (oldest message) | > 5 мин | > 30 мин | Старые сообщения = задержка обработки заказов |
| DLQ size | > 0 | > 10 | Любое сообщение в DLQ требует внимания — потенциально потерянный заказ |

**Почему эти значения:**
- Queue depth: при 1000+ сообщений задержка обработки становится заметной (минуты)
- Messages in flight: 100+ unacked при нормальной скорости обработки — признак проблемы
- DLQ > 0: каждое сообщение в DLQ — потенциальная потеря бизнеса

#### 5. Disk Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| Disk Usage % | > 75% | > 90% | PostgreSQL требует места для WAL, vacuum, temp files |
| Disk I/O Wait | > 20% | > 50% | Высокий iowait = диск не справляется, запросы ждут |

**Почему эти значения:**
- 75% — запас для роста данных и служебных операций БД
- 90% — PostgreSQL может начать отказывать в записи
- iowait > 20% — заметная деградация производительности

#### 6. Network Saturation

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| Network bandwidth utilization | > 70% | > 90% | При насыщении сети растут задержки и потери пакетов |
| TCP connection errors | > 0.1% | > 1% | Ошибки соединений = потенциальные сбои |
