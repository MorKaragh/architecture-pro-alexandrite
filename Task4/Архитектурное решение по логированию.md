# Архитектурное решение по логированию

## Мотивация

### Почему в систему нужно добавить логирование (вот уж не думал что в 2025 придется это объяснять)

Компания «Александрит» находится в критической ситуации: клиенты жалуются на потерянные заказы, операторы - на медленный MES, команда разбирает проблемы "со слов клиента", тратя часы и дни. Система работает "вслепую" без объективных данных.

**Что даст логирование:**
- Быстрая локализация сбоев в распределённой системе
- Возможность ретроспективного анализа сбоев
- Полная трассировка жизненного цикла заказа через все системы
- Проактивное обнаружение проблем до жалоб клиентов (особенно в сочетании с мониторингом)
- Обоснованные решения по оптимизации на основе реальных данных
- И, хоть это и не целевое назначение логов, порой можно из них выудить полезные аналитические данные для принятия бизнес-решений

### Технические и бизнес-метрики 


1. **MTTR (Mean Time To Repair)** - среднее время восстановления
- Основная метрика, ожидается очень сильное ускорение решения проблем. Без нормальных логов понять причину сбоя зачастую очень трудно или вовсе не возможно. Логирование, будучи реализованно коректно, позволит быстро локализовать проблему вплоть до конкретного места в коде, где произошел сбой. 

2. **MTTD (Mean Time To Detect)** - среднее время обнаружения проблемы
- Сейчас проблемы обнаруживаются только после жалоб клиентов, что может занимать часы или дни. Структурированные логи в сочетании с алертингом позволят обнаруживать проблемы автоматически - например, появление сообщений в DLQ или всплеск ошибок. Это даст возможность реагировать на проблемы до того, как они повлияют на клиентов.

3. **% решенных инцидентов** - процент инцидентов, для которых удалось найти причину
- Сейчас многие инциденты остаются неразобранными из-за отсутствия понимания что именно произошло. Записи в логах позволят восстановить последовательность действий и найти причину практически любого инцидента. Это критично для предотвращения повторения проблем.

4. **% потерянных заказов** - процент заказов, которые "зависли"
- Одна из основных жалоб клиентов - заказы "теряются" или зависают на каком-то этапе. Логирование всех переходов статусов заказа позволит выявлять такие случаи проактивно через алерты и быстро находить причину. Это напрямую влияет на бизнес - компания уже потеряла несколько контрактов из-за этой проблемы.

5. **Удовлетворённость клиентов (NPS/CSAT)**
- Проактивное решение проблем и быстрая реакция на инциденты благодаря логам повышают качество сервиса. Клиенты не сталкиваются с проблемами или получают быстрое решение, что напрямую влияет на их удовлетворённость и лояльность.

## Анализ системы и необходимые логи

### Системы, требующие сбора логов

**Критичные:**
- **Shop API** - точка входа для всех заказов (B2C канал), логирование создания заказов и загрузки 3D-файлов критично для трассировки жизненного цикла
- **CRM API** - получает сообщения из RabbitMQ и создаёт заказы, критическая точка в цепочке обработки
- **MES API** - медленный дашборд (основная жалоба операторов), долгие расчёты стоимости (до 30 мин), внешний API "завалил" систему
- **RabbitMQ** - потеря сообщений = потеря заказов (основная жалоба клиентов), необходимо логировать DLQ

**Важные:**
- **Shop DB, MES DB** - логирование медленных запросов и ошибок для выявления узких мест производительности

**Опционально:**
- **S3-хранилище** - логи доступа менее критичны, можно использовать встроенные логи облачного провайдера

### Список необходимых логов (уровень INFO)

#### Примеры ключевых событий с полями:

**Изменение статуса заказа** (все API):
- `timestamp`, `order_id`, `customer_id` (маскированный, например `customer_***123`), `old_status`, `new_status`, `request_id`

**Создание заказа** (Shop API):
- `timestamp`, `order_id`, `customer_id` (маскированный), `status`, `request_id`

**Начало расчёта стоимости** (MES API):
- `timestamp`, `order_id`, `file_id`, `model_complexity` (если доступно), `request_id`

**Завершение расчёта стоимости** (MES API):
- `timestamp`, `order_id`, `calculation_duration_ms`, `price`, `request_id`

**Получение сообщения из RabbitMQ** (CRM API):
- `timestamp`, `message_id`, `order_id`, `event_type`, `correlation_id`

**Сообщение попало в DLQ** (RabbitMQ):
- `timestamp`, `message_id`, `queue`, `reason`, `original_routing_key`

**Медленный запрос к БД** (PostgreSQL):
- `timestamp`, `query` (упрощённый), `duration_ms`, `database`, `user` (маскированный)

### Другие уровни логирования

**ERROR** - используется для:
- Всех исключений с полным stack trace
- HTTP 500 и других серверных ошибок
- Ошибок подключения к БД, RabbitMQ, S3
- Критических бизнес-ошибок

**WARN** - используется для:
- Медленных операций (превышение порога, например запрос > 5 секунд)
- Повторных попыток (retry) при обработке запросов
- Деградации функциональности (fallback)
- Превышения лимитов (rate limiting, но запрос обработан)

**DEBUG** - используется для:
- Детальной отладочной информации (только в dev/release)
- Промежуточных значений в сложных вычислениях
- Деталей работы с БД (SQL-запросы с параметрами, только в dev)

**FATAL** - используется для:
- Системных ошибок, после которых сервис не может продолжать работу
- Потери подключения к критическим ресурсам без возможности восстановления

## Предлагаемое решение

### Технологический стек

**ELK Stack:**
- **Elasticsearch** - централизованное хранилище логов
- **Filebeat** - лёгкий агент для сбора логов с серверов
- **Kibana** - визуализация и анализ
- **Logstash** (опционально) - для сложной обработки и обогащения логов (можно добавить позже при необходимости)

**Формат логов:** JSON (структурированные логи)

### Архитектура

1. **Приложения** пишут структурированные (JSON) логи в файлы
   - Java (Spring Boot): Logback с `logstash-logback-encoder`
   - C# (.NET): Serilog с JSON-форматтером
   - Все логи содержат обязательные поля: `timestamp`, `level`, `service`, `message`, `request_id`

2. **Filebeat** (на каждом сервере) читает логи из файлов и отправляет в Elasticsearch

3. **Elasticsearch** хранит логи в индексах по системе и дате (например, `mes-api-logs-2024-01-15`)

4. **Kibana** предоставляет интерфейс для поиска, анализа и визуализации

**Интеграция:** Логи содержат `trace_id` (из OpenTelemetry) для корреляции с трейсами в Jaeger.

### Изменения при переходе на Kubernetes

После внедрения Kubernetes стек логирования адаптируется под контейнерную среду:

- **Fluent Bit** (или Fluentd) как DaemonSet вместо Filebeat - более лёгкое решение, оптимизированное для Kubernetes, собирает логи из stdout/stderr контейнеров и метаданные подов
- **Сбор логов:** логи из контейнеров собираются автоматически (приложения пишут в stdout/stderr), не требуется настройка файловых путей
- **Elasticsearch и Kibana:** могут быть развёрнуты в кластере через операторы (например, ECK - Elastic Cloud on Kubernetes) или остаться как managed service
- **Обогащение:** Fluent Bit добавляет метаданные Kubernetes (namespace, pod, container) автоматически

Основное преимущество - стандартизация сбора логов через stdout/stderr, упрощение управления через Kubernetes API.

### Интеграция с мониторингом

При внедрении логирования важно учитывать, что в системе уже внедряется мониторинг (Prometheus + Grafana). Необходимо избегать дублирования метрик между логами и мониторингом:

- **Мониторинг (Prometheus)** - для метрик производительности (RPS, latency, CPU, memory, ошибки), которые требуют быстрого доступа и агрегации
- **Логи (Elasticsearch)** - для детального анализа событий, трассировки запросов, разбора инцидентов

**Интеграция:**
- Elasticsearch можно использовать как datasource в Grafana для визуализации данных из логов (например, количество ошибок по типам, распределение заказов по статусам)
- Метрики из логов можно экспортировать в Prometheus через Logstash/Fluentd для создания единых дашбордов
- Корреляция метрик и логов через `request_id` / `trace_id` позволяет переходить от метрики к детальным логам и наоборот

Это даёт единую картину системы: метрики показывают "что происходит", логи - "почему это происходит".

## Политика безопасности

### Обработка чувствительных данных

**Данные, которые НЕ попадают в логи:**
- Пароли, токены, API-ключи
- Полные номера банковских карт (можно последние 4 цифры)
- Паспортные данные
- файлы в base64

**Маскирование:**
- `customer_id`: `customer_***123` (последние 3 цифры)
- `email`: `u***@example.com` (только домен)
- `api_client_id`: `client_***abc` (частичное маскирование)

### Контроль доступа

| Роль | Права доступа |
|------|---------------|
| **Администратор** | Полный доступ ко всем логам, настройка Kibana |
| **Разработчик** | Доступ ко всем логам |
| **DevOps** | Доступ ко всем логам, настройка алертов |
| **Поддержка** | Доступ для поиска по `order_id`, `customer_id` (маскированному) |
| **Аналитик** | Доступ к агрегированным данным (без ПДн), дашборды |

**Реализация:** Роли в Kibana, интеграция с существующей системой аутентификации.

## Политика хранения

### Отдельные индексы под систему

**Структура:** `{service}-logs-{date}` (например, `mes-api-logs-2024-01-15`)

**Преимущества:** Независимое управление жизненным циклом, разные настройки репликации, удобный поиск.

### Сроки хранения

**Обоснование:** Максимальное время обработки заказа - до 2 месяцев (расчёт до 30 мин + производство несколько недель). Храним **вдвое дольше** = **120 дней** для возможности разобрать проблемы.

| Система | Hot (30 дней) | Archive (120 дней) |
|---------|---------------|-------------------|
| MES API, CRM API, RabbitMQ | ✅ | ✅ |
| Shop API | ✅ | 90 дней |
| PostgreSQL | 7 дней | 30 дней |

**Управление:** Index Lifecycle Management (ILM) для автоматического удаления старых данных.

### Размер логов и планирование ёмкости

Приведу для примера, в задании на самом деле нет данных для точного расчёта объемов.

**Оценка:** ~190 MB/день ≈ 6 GB/месяц на систему  
**С учётом репликации:** ~20-30 GB/месяц на все системы  
**За 4 месяца:** ~80-120 GB

**Минимальная конфигурация:** 3 ноды Elasticsearch, 64 GB RAM каждая, 500 GB диска.

## Мероприятия для анализа логов

### Алертинг

**Текущая ситуация (маленькая команда):**
Пока команда небольшая, критичные алерты отправляются всем участникам команды или в общий канал (Slack/Telegram). Для более оперативной реакции можно настроить уведомления тимлиду, архитектору и наиболее активным разработчикам по их желанию.

**Критические алерты (немедленная реакция):**
- Сообщение в DLQ RabbitMQ → уведомление команды
- Высокий error rate (> 5% за 5 минут) → уведомление команды
- Заказ завис (нет логов по `order_id` > порога времени) → уведомление команды
- Потеря сообщения (ожидаемое событие не произошло) → критический алерт

**Предупреждения:**
- Медленная операция (запрос > порога)
- Высокое количество WARN (> 10 за 10 минут)
- Медленный запрос к БД (> 1 секунды)

**Реализация:** Kibana Alerting с интеграцией в Slack/Email/Telegram.

**Перспектива (по мере роста бизнеса):**
При росте команды и появлении выделенной поддержки и дежурных инженеров потребуется более сложная маршрутизация алертов: критичные - дежурному, предупреждения - в канал команды, информационные - по подписке.

### Поиск аномалий

**Типы аномалий для детекции:**

1. **Аномалии нагрузки (DDoS, атаки):**
   - Резкий рост запросов (10x за короткий период, например с 1000 до 10000 в секунду)
   - Много запросов от одного IP/пользователя
   - Алерт: уведомление DevOps, автоматическое включение rate limiting

2. **Аномалии ошибок:**
   - Всплеск ошибок (резкое увеличение ERROR level)
   - Новый тип ошибки
   - Корреляция ошибок в нескольких системах одновременно

3. **Аномалии производительности:**
   - Деградация производительности (постепенное увеличение latency)
   - Внезапное замедление (резкое увеличение latency для эндпоинта)
   - Аномально долгие операции (расчёт стоимости > 30 минут)

4. **Аномалии бизнес-логики:**
   - Заказы "зависают" (не меняют статус > порога)
   - Необычное распределение статусов

**Реализация:** Elasticsearch Machine Learning или кастомные запросы в Kibana с алертами.

### Дашборды

- **Overview Dashboard:** общее состояние системы, распределение по уровням, топ ошибок
- **Order Tracking Dashboard:** поиск заказа по `order_id` с полной трассировкой
- **Error Analysis Dashboard:** топ ошибок по типам, тренд ошибок
- **Performance Dashboard:** latency по эндпоинтам, медленные запросы
- **RabbitMQ Dashboard:** сообщения в DLQ, messages in flight

## Критерии выбора технологии

**Выбранное решение: ELK Stack (Elasticsearch + Filebeat + Kibana)**

| Критерий | ELK | OpenSearch | Splunk | Loki+Grafana | Обоснование выбора ELK |
|----------|-----|------------|--------|--------------|------------------------|
| **Лицензия** | Elastic License (SSPL) | Apache 2.0 | Проприетарная | Apache 2.0 | Бесплатна для self-hosted, контроль над данными |
| **Производительность** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | Оптимизирован для поиска, проверен на больших объёмах |
| **Масштабируемость** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | Отличное горизонтальное масштабирование |
| **Экосистема** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | Огромное сообщество, готовые интеграции (Filebeat, Logstash) |
| **Поддержка структурированных логов** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ | Нативная поддержка JSON, мощный поиск |

| **Простота внедрения** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | Требует настройки, но это разовое вложение |
| **Безопасность** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | Хорошие возможности контроля доступа |

**Почему ELK:**
- Проверенная производительность и масштабируемость
- Богатая экосистема и сообщество
- Нативная поддержка структурированных логов (JSON)
- Бесплатная лицензия для self-hosted
- Интеграция с существующей инфраструктурой (Grafana, Prometheus, Jaeger)

**Компромиссы:**
- Elastic License имеет ограничения на использование в облачных сервисах (но для self-hosted не проблема)
- Требует времени на первоначальную настройку

**Альтернативы:** OpenSearch (если критична полностью открытая лицензия), Loki+Grafana (для меньших объёмов), Datadog (если есть бюджет на SaaS).
